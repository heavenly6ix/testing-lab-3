## 1. Назначение программного продукта

**Исходная формулировка практической работы №2.**

Backend-сервис предназначен для:

- регистрации и авторизации пользователей;
- управления пользовательскими подписками;
- хранения информации о фактических платежах;
- анализа фактических расходов;
- прогноза будущих платежей.

Сервис:
- НЕ выполняет реальные банковские списания;
- НЕ хранит реквизиты банковских карт;
- платежи вводятся пользователем;
- расчёты по разным валютам выполняются отдельно;
- автоматическая конвертация валют не выполняется.

**Границы третьей работы.** Сервис является учебным backend API, а не процессором списаний. Реальная доставка почты, клиентский интерфейс восстановления пароля и гарантии промышленной эксплуатации не выдаются за реализованные возможности.

## 2. Функциональные требования (F01–F15)

### F01 — Регистрация

**Исходная формулировка практической работы №2.**

API регистрации принимает email и пароль, создаёт пользователя с уникальным ID. Повторный email после нормализации регистра и пробелов должен возвращать HTTP 409 и не создавать запись.

**Уточнения практической работы №3.**

Адрес нормализуется удалением пробелов по краям и приведением к нижнему регистру независимо от языковых настроек; точки и суффиксы почтовых провайдеров не удаляются. Длина адреса после удаления пробелов — не более 254 символов, формат проверяется. При регистрации пароль имеет длину 12–128 символов, его пробелы и регистр не изменяются. Уникальность нормализованного адреса обеспечивается ограничением БД, включая конкурентную регистрацию. Неверный ввод — HTTP 400, повторный адрес — HTTP 409; пароль, хеш и соль в ответ не включаются.

### F02 — Вход

**Исходная формулировка практической работы №2.**

API входа выдаёт access- и refresh-токены при корректных учётных данных. Неверные данные возвращают HTTP 401 без указания, существует ли email.

**Уточнения практической работы №3.**

Неизвестный адрес и неверный пароль при корректном запросе дают одинаковые код и сообщение HTTP 401; ошибка структуры или отсутствие обязательного поля — HTTP 400. Превышение лимита — HTTP 429 по N04, недоступная обязательная БД — HTTP 503 по R05. Токен доступа — подписанный JWT со сроком не более 15 минут. Токен обновления непрозрачный, содержит не менее 32 случайных байтов; в БД хранится его хеш. Абсолютный срок новой сессии — не более 30 дней. Ответ содержит сроки истечения; ответы с токенами не кэшируются и не журналируются. Равенство сообщений не доказывает одинаковое время выполнения.

### F03 — Обновление сессии

**Исходная формулировка практической работы №2.**

Обновление сессии выдаёт новую пару токенов и делает использованный refresh-токен недействительным. Повторное использование токена должно отклоняться.

**Уточнения практической работы №3.**

Ротация атомарна: при двух конкурентных запросах успешен только один. Неверный, истёкший, использованный или отозванный токен обновления возвращает одинаковый HTTP 401. Новый токен не продлевает абсолютный 30-дневный срок сессии; доступ по JWT остаётся ограничен собственными 15 минутами. Повтор старого токена сам по себе не отзывает уже выданную новую пару. Изменение записей токенов транзакционно.

### F04 — Выход

**Исходная формулировка практической работы №2.**

Выход отзывает refresh-токен текущей сессии. После выхода обновление сессии этим токеном невозможно.

**Уточнения практической работы №3.**

Отзывается цепочка обновления предъявленной сессии, остальные сессии сохраняются. Операция принимает токен обновления без обязательного Bearer, чтобы истёкший токен доступа не мешал выходу. Повторный выход и неизвестный корректно оформленный токен дают одинаковый успешный HTTP 204. Ранее выданный токен доступа может действовать до собственного истечения; мгновенный отзыв JWT не обещается.

### F05 — Восстановление пароля

**Исходная формулировка практической работы №2.**

Восстановление пароля использует одноразовую ссылку сроком 15 минут. После успешной смены пароля все refresh-токены пользователя отзываются. Ответ запроса восстановления одинаков для известных и неизвестных email.

**Уточнения практической работы №3.**

Для синтаксически корректного известного и неизвестного адреса запрос восстановления даёт одинаковые HTTP 202 и тело. Токен восстановления хранится в виде хеша, действует 15 минут, не возвращается в ответе запроса восстановления и не журналируется. Новый запрос делает прежние неиспользованные токены пользователя недействительными. В учебном режиме абстракция отправителя заменяется почтовым ящиком в памяти без публичного маршрута чтения писем. Смена пароля, использование токена и отзыв всех токенов обновления выполняются одной транзакцией. Неверный, истёкший или использованный токен даёт одинаковый HTTP 400; при точном достижении срока он уже недействителен. Конкурентные запросы не могут оба сменить пароль. Политика ранее выданных JWT совпадает с F04.

### F06 — Создание подписки

**Исходная формулировка практической работы №2.**

Авторизованный пользователь может создать подписку.

Обязательные параметры:
- название 1–100 символов;
- положительная сумма;
- валюта RUB, USD или EUR;
- период месяц или год;
- дата начала;
- дата следующего платежа;
- категория.

Некорректные данные возвращают HTTP 400 без создания записи.

**Уточнения практической работы №3.**

Название после удаления пробелов по краям содержит 1–100 символов, категория — 1–50; категория является пользовательской строкой. Суммы имеют тип decimal, не более двух значащих дробных разрядов и диапазон 0 < amount ≤ 999999999.99; лишние разряды отклоняются без скрытого округления. Валюты — RUB/USD/EUR, периоды — monthly/yearly. NextPaymentDate ≥ StartDate; начальная дата следующего платежа может быть в прошлом. Начальное состояние active, признак archived=false. По NextPaymentDate сохраняются исходные расчётные день и месяц. Владелец определяется аутентификацией, а не телом запроса.

### F07 — Получение подписок

**Исходная формулировка практической работы №2.**

API возвращает только подписки текущего пользователя.

Нужны:
- фильтр по статусу;
- фильтр по категории;
- сортировка по дате следующего платежа;
- пагинация 1–100 записей.

Попытка получить чужой объект должна выглядеть как отсутствие объекта и возвращать HTTP 404.

**Уточнения практической работы №3.**

Обычный список исключает архив; includeArchived явно включает его. Сортировка — NextPaymentDate по возрастанию, затем Id. По умолчанию page=1 и pageSize=20; допустимы page≥1 и pageSize от 1 до 100, иначе HTTP 400 без автоматического ограничения. Страница за концом возвращает пустой список и общее число подходящих записей. Категория сравнивается точно с учётом регистра после удаления пробелов по краям. Собственный архив доступен по идентификатору; чужой и отсутствующий объект одинаково дают HTTP 404. Неверный формат идентификатора — HTTP 400.

### F08 — Изменение подписки

**Исходная формулировка практической работы №2.**

Пользователь может изменять:
- название;
- сумму;
- валюту;
- период;
- категорию;
- будущую дату платежа.

Изменение подписки не должно изменять уже сохранённые фактические платежи.

**Уточнения практической работы №3.**

Меняются собственные неархивные активные и приостановленные подписки. Явно новая NextPaymentDate строго позже текущего дня UTC и не раньше StartDate. Смена периода требует одновременно новую дату; изменение других полей не требует переписывать уже прошедшую прежнюю дату. Владелец и StartDate не меняются. Явная новая дата задаёт новый исходный расчётный день/месяц; изменение суммы, валюты, имени или категории его не переносит. Отменённая или архивная подписка неизменна для этих операций — HTTP 409. Сохранённые поля фактов, включая снимки названия и категории, не переписываются. Внесение факта платежа само не двигает расписание. В PATCH пропуск поля не меняет его, явный null, неизвестные поля и пустой объект дают HTTP 400.

### F09 — Изменение состояния подписки

**Исходная формулировка практической работы №2.**

Подписку можно:
- приостановить;
- возобновить;
- отменить.

Статус сохраняется.

Приостановленные и отменённые подписки не входят в прогноз будущих платежей.

**Уточнения практической работы №3.**

Переходы: active → paused, paused → active, active/paused → cancelled. Повтор команды уже установленного целевого состояния безопасен. Cancelled окончателен: resume/pause дают HTTP 409; для архива команды состояния также запрещены с HTTP 409. Возобновление не переносит исходный расчётный день и не создаёт факты пропущенных оплат. Чужая/отсутствующая подписка — HTTP 404.

### F10 — Архивация подписки

**Исходная формулировка практической работы №2.**

Удаление подписки реализуется как архивация.

Архивная подписка:
- скрывается из обычного списка;
- сохраняет историю платежей;
- её фактические платежи продолжают участвовать в аналитике расходов.

**Уточнения практической работы №3.**

Удаление устанавливает Archived=true без физического удаления подписки, платежей или аудита; Status сохраняется отдельно. Собственную подписку можно архивировать в любом из трёх состояний, повтор безопасен и даёт HTTP 204. Архив скрыт из обычного списка и прогноза; собственный объект и история доступны. Исторические успешные неаннулированные факты входят в расходы. Внесение пропущенного ручного платежа разрешено по F11, изменение расписания запрещено. Разархивация и физическое удаление в объём не добавлены.

### F11 — Регистрация фактического платежа

**Исходная формулировка практической работы №2.**

Для собственной подписки пользователь может зарегистрировать фактический платёж.

Поля:
- положительная сумма;
- валюта должна совпадать с валютой подписки;
- дата;
- статус «успешный» или «неуспешный».

Использовать `Idempotency-Key`.

Одинаковый ключ + одинаковое тело:
- возвращает первоначальный результат;
- не создаёт дубль.

Одинаковый ключ + другое тело:
- HTTP 409.

**Уточнения практической работы №3.**

Факт разрешён для собственной подписки, включая paused/cancelled/archived. Дата не позже текущего дня UTC; произвольная нижняя граница не вводится, платёж до StartDate допустим. Для нового факта валюта совпадает с текущей валютой подписки. Отдельно сохраняются сумма, валюта, дата, состояние, владелец/подписка, время создания/изменения, признак аннулирования, снимки названия и категории.

Idempotency-Key обязателен: 1–128 видимых ASCII без пробелов, регистр значим. Область — пользователь и операция создания платежа; SubscriptionId входит в сравнение. Сравниваются типизированные значения: порядок/пробелы JSON и 1.0/1.00 не создают различий, серверные время и автор не входят в сравнение. Повтор возвращает первоначальные HTTP 201, тело и Id без второго факта/аудита, даже после исправления/аннулирования факта или изменения/архивации подписки. Иная подписка или данные при том же ключе — HTTP 409; другой ключ — новая операция. Ключи сохраняются весь срок хранения учебной БД. Платёж, запись ключа с первоначальным ответом и аудит создаются атомарно по R04; конкурентные повторы не дублируют запись. Ошибки валидации и отменённая транзакция не закрепляют успешный результат. Пользовательское состояние failed — сохранённый факт, а не ошибка HTTP-записи.

### F12 — История платежей

**Исходная формулировка практической работы №2.**

История платежей доступна с:
- фильтром по подписке;
- фильтром по статусу;
- диапазоном дат;
- пагинацией.

Возвращаются только платежи текущего пользователя.

**Уточнения практической работы №3.**

Границы дат включены; допустимы одна граница или отсутствие обеих, начало не позже конца. Предел 366 дней относится к аналитике и не переносится на историю. Сортировка — дата по убыванию, затем Id; пагинация как F07. Видны также аннулированные факты и история архива с явными признаками. Чужая/несуществующая подписка в фильтре — HTTP 404, неверные фильтры — HTTP 400, пустая выборка — успешный пустой результат.

### F13 — Исправление, аннулирование и аудит

**Исходная формулировка практической работы №2.**

Платёж можно:
- исправить;
- аннулировать.

Необходимо сохранять:
- автора изменения;
- время;
- предыдущие значения.

Аннулированный платёж не участвует в аналитических итогах.

**Уточнения практической работы №3.**

Исправляются Amount, Date и Status у неаннулированного факта; Currency, SubscriptionId, UserId и снимки названия/категории неизменны. Историческая валюта не сверяется с новой валютой подписки при коррекции. Аннулирование ставит IsVoided=true без удаления; повтор безопасен и не создаёт второй аудит. Исправление или восстановление аннулированного факта даёт HTTP 409. Архив подписки не мешает исправлению истории. Каждое реальное изменение дополняет аудит автором, действием, временем UTC, предыдущим и новым состоянием; при создании предыдущее отсутствует. Изменение и аудит атомарны, прежние записи аудита не переписываются. Аудит читает только владелец.

### F14 — Аналитика расходов

**Исходная формулировка практической работы №2.**

Аналитика за период возвращает:

- сумму успешных неаннулированных платежей;
- разбивку по месяцам;
- разбивку по категориям;
- разбивку по подпискам;
- результаты отдельно для каждой валюты.

Пустой период возвращает нулевые итоги.

**Уточнения практической работы №3.**

Обязательны from/to; диапазон [from,to] включителен, to−from+1≤366 дней. Учитываются только собственные successful и !IsVoided факты; состояние/архив подписки прошлый расход не исключают. Месяц — YYYY-MM, категория — сохранённый снимок, подписка — Id совместно с валютой. Валюты никогда не смешиваются в один денежный итог. Общие итоги всегда содержат RUB/USD/EUR с нулями для отсутствующих валют; пустые разбивки — пустые массивы. Месяцы без расходов автоматически не добавляются. Неверные/обратные/слишком длинные границы — HTTP 400.

### F15 — Прогноз платежей

**Исходная формулировка практической работы №2.**

API прогноза показывает платежи активных подписок на ближайшие 30 дней.

Ответ содержит:
- дату;
- подписку;
- сумму;
- валюту;
- итоги по валютам.

Для исходного дня 29–31:
если такого дня в месяце нет, используется последний день этого месяца;
в следующем месяце расчёт снова должен выполняться от исходного расчётного дня.

**Уточнения практической работы №3.**

Окно — [сегодня UTC, сегодня UTC+30 дней), включая сегодняшний день и исключая верхнюю границу. Берутся только собственные active и !Archived подписки. Каждая дата считается от исходных дня/месяца, а не от предыдущего сокращения: 31 января → 28/29 февраля → 31 марта; ежегодное 29 февраля возвращается к 29 в следующем високосном году. Кандидаты до StartDate/NextPaymentDate не создаются, прошлые даты не выдаются; прогноз ничего не переписывает в БД. Сумма и валюта — текущие параметры подписки; ручной факт не сдвигает и не подавляет событие. В окне могут быть два ежемесячных события одной подписки. Порядок — дата, затем Id подписки; итоги RUB/USD/EUR разделены, при отсутствии событий равны нулю. Публичное произвольное окно прогноза не добавлено.

## 3. Нефункциональные требования (N01–N10)

### N01 — Защита транспортного соединения

**Исходная формулировка практической работы №2.**

Внешний API должен поддерживать HTTPS с TLS 1.2+.

Для локальной разработки допускается HTTP localhost, если отдельно указано, что это development-режим.

**Уточнения практической работы №3.**

HTTP разрешён только для локального режима разработки на петлевом адресе. Такая проверка не подтверждает TLS внешнего размещения; сертификат, протокол и внешняя среда проверяются отдельно.

### N02 — Хранение паролей

**Исходная формулировка практической работы №2.**

Пароли не хранить в открытом виде.

Использовать Argon2id с индивидуальной случайной солью не менее 16 байт, если это практически реализуемо выбранной библиотекой.

Если используется другая безопасная стандартная реализация ASP.NET Core PasswordHasher, отдельно объяснить отклонение от исходного требования.

**Уточнения практической работы №3.**

Argon2id остаётся основным вариантом с криптографически случайной индивидуальной солью и сохраняемыми параметрами хеша; собственная криптография не разрабатывается. Замена на PasswordHasher не принималась. Функциональная совместимость библиотеки отделяется от независимого аудита и измерения её стоимости.

### N03 — Сроки и проверка токенов

**Исходная формулировка практической работы №2.**

Access token ≤ 15 минут.

Refresh token ≤ 30 дней.

Проверять:
- подпись;
- issuer;
- audience;
- expiration.

**Уточнения практической работы №3.**

Токен обновления ограничен абсолютным сроком сессии и не получает новые 30 дней при ротации. Проверяются также допустимый алгоритм и идентификатор пользователя; ClockSkew=0. При now≥expiresAt токен недействителен, время UTC. Секреты обновления/восстановления хранятся как хеши; ключ подписи не помещается в репозиторий, отчёт или журналы. Срок восстановления — отдельно 15 минут по F05.

### N04 — Ограничение попыток входа

**Исходная формулировка практической работы №2.**

Не более:
- 5 неудачных попыток входа на аккаунт за 15 минут;
- 30 попыток на IP за 15 минут.

После превышения:
HTTP 429 + `Retry-After`.

Если IP-rate-limit существенно усложняет учебную реализацию, сначала предложить способ реализации и отметить стоимость требования. Не удалять его молча.

**Уточнения практической работы №3.**

Окно скользящее, 15 минут. Первые пять неверных проверок дают HTTP 401; при пяти неудачах следующая попытка того же нормализованного адреса — HTTP 429, даже с правильным паролем. Первые 30 попыток по IP допускаются дальше, 31-я — HTTP 429. Неизвестные адреса учитываются аналогично. Успех не стирает неудачи; попытка возрастом не менее 15 минут исключается. Заблокированные самим IP запросы его окно не продлевают; отклонённые по аккаунту учитываются по IP, но не добавляют новую проверку пароля. Retry-After округляется вверх до целых секунд, минимум 1; при двух запретах берётся больший срок.

Принято учебное упрощение: состояние аккаунта сохраняется в SQLite, состояние IP — в памяти одного процесса и теряется при перезапуске; распределённая гарантия не заявлена. Произвольному X-Forwarded-For не доверяют, часы подменяемы. В ревью стоимость описана составом работ: дополнительный обработчик, атомарные счётчики, очистка состояния, проверки времени и конкурентности; для нескольких процессов нужно общее атомарное хранилище. Оценка часов не выдумывалась.

### N05 — Производительность

**Исходная формулировка практической работы №2.**

Требование производительности:
- p95 CRUD ≤ 300 мс;
- аналитика ≤ 1 с;
- 5xx < 1%;
- 100 req/s;
- 100 параллельных клиентов;
- 1 млн платежей.

На данном этапе не заявлять выполнение этого требования без реального нагрузочного теста.

Отнести его к требованиям, требующим отдельного performance testing.

**Уточнения практической работы №3.**

Численные цели сохранены для отдельного нагрузочного испытания. Нужны профиль операций, данные, прогрев, длительность, оборудование и расчёт ошибок. В третьей работе предложено уточнить предел аналитики как 95-й процентиль ≤1 с; исходная N05 процентиль аналитики не задавала. Это предложение к плану испытаний, а не результат измерения и не основание объявить N05 выполненным.

### N06 — Форматы данных

**Исходная формулировка практической работы №2.**

API:
- JSON UTF-8;
- `/api/v1`;
- DateTime в ISO 8601 UTC;
- даты как YYYY-MM-DD;
- денежные значения через `decimal`, не `double`.

**Уточнения практической работы №3.**

Исходное требование сохранено. Календарные дни отделены от отметок времени: DateOnly для дат, UTC с Z для времени создания/изменения и токенов. Денежные хранение и агрегация должны сохранять точность, без перехода к double или арифметике SQLite REAL. Дополнительные пределы сумм принадлежат уточнениям F06/F11.

### N07 — Ограничения запросов

**Исходная формулировка практической работы №2.**

Ограничения:
- request body ≤ 1 MiB;
- page size ≤ 100;
- аналитический диапазон ≤ 366 дней.

Документировать HTTP 400/413.

**Уточнения практической работы №3.**

1 MiB — 1 048 576 фактически прочитанных байтов, в том числе без Content-Length и при передаче частями; превышение — HTTP 413. Неверная пагинация и диапазон — HTTP 400; длительность аналитики считается включительно. Единая ошибка ограничена HTTP-конвейером приложения, а не транспортными ошибками до него.

### N08 — Корреляция и журналирование

**Исходная формулировка практической работы №2.**

Каждый ответ должен иметь correlation ID.

Логи:
- route;
- status;
- duration;
- correlation ID.

Не логировать:
- пароль;
- токены;
- секреты;
- тело регистрации.

**Уточнения практической работы №3.**

Ответы, сформированные приложением, включая ошибки, содержат X-Correlation-ID; тело ошибки содержит тот же correlationId. Внешний идентификатор проверяется: 1–64 ASCII — буквы, цифры, дефис, подчёркивание; иначе создаётся новый. Записываются шаблон маршрута, статус, длительность и идентификатор. Строка запроса с секретом, тело, Authorization, токены, ключ подписи, письмо восстановления, стек и внутренние пути не раскрываются.

### N09 — Контейнеризация

**Исходная формулировка практической работы №2.**

Проект должен быть пригоден для контейнеризации.

Добавить Dockerfile, если это не мешает основной работе.

Не заявлять успешную проверку Linux x64/arm64 без фактического запуска.

**Уточнения практической работы №3.**

Предусмотрены Dockerfile, внешняя конфигурация и отдельный путь/том SQLite. Подготовка контейнеризации не равна реальной сборке/запуску и проверке Linux обеих архитектур; отсутствие подтверждения отражается как частичное выполнение.

### N10 — Документация API

**Исходная формулировка практической работы №2.**

OpenAPI должен содержать:
- endpoints;
- request/response schemas;
- status codes;
- authorization.

**Уточнения практической работы №3.**

Документируются параметры, тела, схемы ответов/ошибок, HTTP-коды и защищённость каждой операции; Swagger UI используется локально в режиме разработки. Уточнение от 26.11.2026: у защищённой операции нужно именно "security":[{"Bearer":[]}], а не просто непустой массив [{}]. У публичной операции требование отсутствует или пустое; глобальный обязательный Bearer не вводится. Схема имеет type=http, scheme=bearer, bearerFormat=JWT. Уточнение не меняет серверную авторизацию.

## 4. Требования к качеству (Q01–Q05)

### Q01 — Позитивные и негативные проверки

**Исходная формулировка практической работы №2.**

Для F01–F15 должны быть предусмотрены позитивные и негативные проверки.

Не обязательно превращать все 30+ случаев именно в unit tests, если часть требований относится к HTTP/API.

Разделить:
- unit tests;
- integration/API tests;
- smoke tests.

**Уточнения практической работы №3.**

Исходное требование сохранено. Модульные проверки без HTTP/БД, проверки настоящего HTTP-конвейера с отдельной SQLite и запросы curl к отдельному процессу учитываются раздельно. План не считается успешным выполнением; отсутствующие проверки и результаты не приписываются.

### Q02 — Покрытие бизнес-логики

**Исходная формулировка практической работы №2.**

Модули:
- аналитики расходов;
- прогноза платежей

должны быть покрыты тестами минимум на 90% ветвей.

Обязательно проверить:
- високосный год;
- конец месяца;
- пустой период;
- разные валюты;
- аннулированные платежи.

**Уточнения практической работы №3.**

Порог ≥90% ветвей проверяется для аналитики и прогноза по отдельности. В знаменатель входит бизнес-логика; исключение автоматически созданного кода, миграций, DTO без логики, точки входа и инфраструктурного шаблонного кода обосновывается. Отдельная общая цель третьей работы — >80% ветвей и >90% операторов. Строки не называются операторами; при отсутствии точной метрики операторов/инструкций это прямо указывается.

### Q03 — Абстракции и изоляция тестов

**Исходная формулировка практической работы №2.**

Бизнес-логика должна зависеть от абстракций.

Unit tests не должны требовать:
- сети;
- реальной внешней БД;
- отправки email.

**Уточнения практической работы №3.**

Исходное требование сохранено. Тестируется настоящий сервис, Moq заменяет только зависимости: хранилище, часы, выдачу токенов, отправителя писем и другие порты. Настоящая SQLite-транзакция проверяется интеграционно, не называется модульным тестом. Бизнес-сервисы не зависят напрямую от HTTP/EF Core.

### Q04 — Единый формат ошибок

**Исходная формулировка практической работы №2.**

Ошибки API должны иметь единый формат:

```json
{
  "code": "...",
  "message": "...",
  "correlationId": "...",
  "fields": {}
}
```

`fields` обязательно только для ошибок валидации.

**Уточнения практической работы №3.**

Исходная схема сохранена. Поле fields обязательно для ошибок валидации HTTP 400 и не включается в другие ошибки текущего контракта. HTTP 401 сохраняет заголовок аутентификации, HTTP 429 — Retry-After. Стек, секреты и пути БД не раскрываются. Проверяются также ошибки аутентификации, размера, ограничений и БД.

### Q05 — Готовность сборки и проверка владельца

**Исходная формулировка практической работы №2.**

Перед финальной сдачей:
- сборка без ошибок;
- желательно без предупреждений;
- нет доступа к чужим ресурсам;
- основные маршруты с resource ID должны проверять ownership.

**Уточнения практической работы №3.**

Исходное требование сохранено. Пользователь определяется проверенной аутентификацией, не телом запроса. Проверка владельца распространяется на чтение, изменение, состояния, архив, внесение факта, фильтр истории по подписке, исправление, аннулирование и аудит. Чужой и отсутствующий объект одинаково дают HTTP 404.

## 5. Требования к надёжности (R01–R05)

### R01 — Доступность

**Исходная формулировка практической работы №2.**

Availability ≥ 99.5%.

Не выдавать это за проверенный результат лабораторной без длительного мониторинга.

Описать как эксплуатационное требование.

**Уточнения практической работы №3.**

Показатель сохранён как эксплуатационный. В третьей работе предложен календарный месяц оценки; среда, период и правила учёта недоступности требуют согласования эксплуатационного соглашения. Короткий запуск, проверка состояния и успешные тесты не доказывают 99,5%.

### R02 — Резервное копирование

**Исходная формулировка практической работы №2.**

Ежедневный backup БД и transaction log ≤ 15 минут.

Для SQLite определить реалистичную учебную интерпретацию либо отметить требование как production-level.

**Уточнения практической работы №3.**

Исходные ежедневная копия и интервал журнала сохранены. Для учебной SQLite предложены согласованные снимки через Online Backup API либо эквивалент не реже 15 минут и отдельная ежедневная копия. Это интерпретация механизма, а не доказательство архивирования журнала или восстановления на произвольный момент. WAL не считается копией. Расписание, хранение, сроки удержания и проверка восстановления остаются отдельной работой.

### R03 — Потери данных и время восстановления

**Исходная формулировка практической работы №2.**

RPO ≤ 15 минут, RTO ≤ 60 минут.

Не заявлять выполнение без восстановления backup.

**Уточнения практической работы №3.**

Цели сохранены без объявления выполненными. Нужны настоящая копия, её возраст, восстановление в новое хранилище, проверка целостности, запуск API и замер времени. Заявленной частоты копирования недостаточно.

### R04 — Атомарность операций

**Исходная формулировка практической работы №2.**

Создание платежа + idempotency key + audit должны быть атомарными.

Использовать транзакцию.

Проверить unit/integration тестом отсутствие частичного результата.

**Уточнения практической работы №3.**

В одной транзакции SQLite создаются факт, запись ключа с первоначальным ответом и аудит создания. Уникальность защищает область ключа, при отмене не остаются частичные записи. Исправление/аннулирование также атомарны с аудитом. Модульная проверка обращения к порту не заменяет настоящий интеграционный сбой после промежуточной записи. Успешный HTTP-ответ только после подтверждённого сохранения.

### R05 — Недоступность БД

**Исходная формулировка практической работы №2.**

При недоступной БД:
- HTTP 503;
- не сообщать об успешной записи;
- приложение не должно падать.

**Уточнения практической работы №3.**

Распознаваемые ошибки недоступности, занятости и ввода-вывода БД дают обобщённый HTTP 503. Валидация остаётся HTTP 400, конфликты — HTTP 409 либо первоначальный результат, ошибки программы — HTTP 500, а не замаскированный 503. После восстановления БД последующие запросы работают. Если подтверждение завершения транзакции потеряно, отсутствие записи не обещается; повторяют тот же ключ для разрешения неопределённости.

При составлении настоящего документа новые сборки, тесты и запуски не выполнялись.

## 9. Ограничения текущей реализации

| Область | Зафиксированное ограничение | Требования |
|---|---|---|
