## Ключевые конфликты и выбранные предложения

1. **Исторические данные и редактирование подписки (F08/F11/F13/F14).** Платёж хранит собственные amount/currency/category/name snapshots. Для нового факта используется валюта и категория подписки на момент регистрации; дата факта может быть раньше регистрации. Исправляется сам факт, а не исходная подписка. Смена валюты подписки не пересчитывает историю и не мешает исправить сумму старого платежа в его сохранённой валюте. Это единая предлагаемая политика; группировка старых расходов по *нынешней* категории будет другим контрактом.
2. **Неизменный idempotency-result и изменяемый payment (F11/F13/R04).** Первый успешный ответ хранится вместе с ключом; replay не возвращает новое состояние после correction/void. Текущее состояние доступно в history. Нельзя просто повторно прочитать изменённую строку и назвать её первоначальным результатом.
3. **Календарь (F15/N06).** Период прогноза — 30 календарных дат UTC, `[today,today+30)`. Для месяца day-anchor, для года также month-anchor. Пример: 31 Jan → 28/29 Feb → 31 Mar; annual 29 Feb → 28 Feb невисокосного года → 29 Feb следующего високосного. Прогноз read-only, факты не «закрывают» расписание автоматически.
4. **Logout/reset и JWT (F04/F05/N03).** Отзываются refresh. Уже выданный access остаётся до 15 минут. Для немедленной инвалидизации access потребуется дополнительное требование и проверка сессии/версии на каждом запросе; такого обещания здесь нет.
5. **Контроль аутентификации (N04/F02/Q04).** 401 не различает наличие email. 429 сигнализирует о лимите; bucket для любого нормализуемого email существует одинаково. Приоритет ограничений/валидации будет явно описан в API-контракте, чтобы не вычислять существование аккаунта по статусу.
6. **Backup и RPO (R02/R03).** Daily backup сам по себе не обеспечивает 15 минут потери. Для SQLite предлагается отдельная интерпретация частых snapshots; это не удаление production PITR и не заявленный рабочий backup-сервис.

## N04: реализация и стоимость без удаления IP-limit

Предлагается один экземпляр учебного API. IP-limit — ранний application middleware по RemoteIpAddress, с потокобезопасной очередью меток разрешённых попыток на каждый IP, точным rolling-окном 15 минут и очисткой неактивных ключей. Не доверять произвольному X-Forwarded-For; proxy headers разрешаются только от настроенного trusted proxy. Account-limit — отдельная абстракция хранилища неуспешных login по normalized email, включая неизвестные адреса. Для сохранения account-limit при рестарте можно хранить failure timestamps в SQLite; при недоступности этого хранилища login завершается 503, а не «успехом без проверки лимита».

На 5-й неверной проверке ещё 401; пока в окне остаются 5 неудач, последующие попытки этого email получают 429, независимо от правильности нового пароля. IP допускает до 30 попыток login в окне; 31-я блокируется. IP учитывает попытки, включая успешно вошедших и отклонённых account-limit; блокированные самим IP запросы не продлевают окно. Retry-After — целое число секунд округлённое вверх до освобождения соответствующего лимита, минимум 1; если оба лимита запрещают запрос, брать больший срок. Успешный login не стирает неудачи rolling-окна.

Стоимость относительно простого login: дополнительный middleware, атомарное обновление счетчиков, bounded lifetime ключей, отдельные clock/concurrency/API-тесты границ окна; для нескольких процессов потребуется общее атомарное хранилище и доверенная конфигурация proxy. Это оценка состава работ, не выдуманные часы. Ограничение: in-memory IP-state теряется при рестарте и не глобален для нескольких процессов — явно предлагаемое учебное упрощение, требующее согласования. N04 не удалено и не помечено выполненным.

ASP.NET Core поддерживает middleware и политики rate limiting, однако наличие готового middleware не доказывает правило «только неудачные попытки аккаунта» или точное rolling-окно; их необходимо проверить отдельно. [Microsoft: rate limiting](https://learn.microsoft.com/en-us/aspnet/core/performance/rate-limit?view=aspnetcore-10.0).

## Криптография, SQLite, документация

Argon2id остаётся целевым алгоритмом. 16-байтная соль согласуется с рекомендацией RFC; выбор пакета, стоимость hash и параметры ещё не проверены на .NET 10/macOS. Возможная отправная точка RFC для ограниченной памяти — 64 MiB, 3 прохода, 4 lanes, 32-byte tag; это кандидат для последующего измерения, не применённая настройка и не результат benchmark. [RFC 9106, разделы 3.1 и 4](https://www.rfc-editor.org/rfc/rfc9106.html).

Для SQLite backup предлагается Online Backup API или эквивалентный корректный snapshot, не простое копирование работающего файла. Документация описывает копию согласованного состояния; выбор частоты/хранения/проверки восстановления остаётся отдельной работой. [SQLite Backup API](https://sqlite.org/backup.html).

Слово «операторы» из PDF не заменяется словом «строки». На этапе coverage необходимо проверить метрики выбранного инструмента; если точных statement/instruction данных нет, отдельно сообщить line/branch и ограничение. Сейчас никакие проценты второй части не измерялись.

## Результат этапа

Все 35 исходных ID сохранены. Подготовлен проект итогового ТЗ с явным разделением unchanged / clarified / educational simplification / production-only. F01–F15 не сокращены, внешние банковские списания/карточные реквизиты/FX не добавлялись. Для F01–F15 подготовлен план позитивных/негативных проверок; ни один из этих тестов ещё не запускался.

Обязательные решения для рассмотрения: политика snapshots и replay; окно прогноза/anchor; терминальность cancel; archived payments; абсолютная длительность сессии; in-memory IP-limit одного процесса; backup как учебный snapshot; Argon2id без преждевременной замены PasswordHasher. После ответа пользователя — этап 2 API, затем отдельная остановка; backend только после утверждения обоих документов.
