## 1. Назначение и границы

Сервис регистрирует/авторизует пользователей, хранит их подписки и введённые вручную фактические платежи, рассчитывает расходы и прогноз расписания. Реальных списаний и интеграции с банками нет. Карточные реквизиты не запрашиваются и не хранятся. RUB/USD/EUR не конвертируются; суммы разных валют никогда не складываются в один денежный итог.

Целевой стек: C# / .NET 10 / ASP.NET Core Web API, SQLite для локального учебного хранения, NUnit/Moq, OpenAPI и Swagger UI для локального Development. Реальные письма заменяются интерфейсом с тестовой/in-memory реализацией по разрешению исходного запроса. Архитектура и создание solution относятся к этапу 3, не к текущему этапу.

Первая часть, её README, отчёт, исходники и artifacts остаются неизменными. Весь новый материал располагается в `part2/`; пути `docs/` и `artifacts/` далее относительны к этой папке. Word-отчёт не создаётся без отдельного запроса.

## 3. Общие правила данных и поведения

Эти решения дополняют связанные F/N и подлежат согласованию вместе с ними:

- Время задаётся абстракцией clock. Текущий календарный день — UTC date этого времени. StartDate/NextPaymentDate/PaymentDate — календарные даты `YYYY-MM-DD`; CreatedAt/UpdatedAt/audit/token expiry — UTC timestamps ISO 8601 с `Z`. Часовой пояс компьютера не меняет бизнес-границы.
- Денежное значение — `decimal` на всём пути бизнес-вычислений; 2 знака после точки, диапазон `0 < amount ≤ 999999999.99`. Лишние ненулевые дробные знаки дают 400, не скрытое округление; численно `1.0` и `1.00` равны. JSON decimal не читается через double. Хранение и агрегация SQLite должны сохранять точность; преобразование в REAL для подсчёта итогов не допускается.
- Name после trim — 1–100 символов, Category после trim — 1–50. Категория — пользовательская строка, справочник категорий не требуется. Сопоставление category — точное ordinal после trim, регистр значим. Currency — только RUB, USD, EUR. BillingPeriod — месяц или год. Wire-значения enum будут закреплены в API-контракте.
- Даты и суммы валидируются до записи. У фактического платежа дата не позже UTC today; это **предлагаемое дополнительное ограничение** слова «фактический». Произвольную нижнюю календарную границу для исторического платежа не вводим. Платёж до StartDate допустим как ручной исторический факт; forecast не генерирует даты до StartDate.
- UserId и actor ID получаются только из аутентификации; клиент не выбирает владельца. Для любого чужого resource ID поведение равно отсутствующему объекту (404). Неподдерживаемые значения фильтров/enum/дат/денег → 400.
- Пагинация: page по умолчанию 1, pageSize по умолчанию 20, page ≥1, pageSize 1–100; превышение/отрицательные значения — 400, не silent clamp. Страница за концом выдаёт пустой items, total — число всех подходящих строк. Сортировка имеет уникальный tie-breaker по ID.
- Контракт первоначального idempotency-response не меняется после изменения текущего ресурса. Разрешение конфликтов одновременного редактирования без клиентской версии — последнее успешно зафиксированное изменение; before-values для audit снимаются в той же транзакции. Optimistic concurrency/ETag не заявлены частью этого учебного объёма.

## 4. Функциональные требования

### F01 — Регистрация

Валидные email/password создают одного пользователя с уникальным ID. Email нормализуется `Trim` + invariant lower-case, без удаления точек/plus-суффиксов и без правил отдельных провайдеров; длина после trim ≤254, формат валидируется. Пароль не обрезается и не меняет регистр; предлагаемая длина 12–128 символов, без выдуманных требований состава. Остальные правила хеширования — N02.

Одинаковый normalized email → 409, новая запись не создаётся, в том числе при конкурентной регистрации. Требуется уникальное ограничение БД, предварительного поиска недостаточно. В ответах нет password/hash/salt. Некорректный ввод → 400. Нормализация применяется одинаково в register/login/forgot и account-rate-limit.

### F02 — Вход

Валидные credentials выдают access и refresh вместе с информацией об expiry. Неверный email/password, включая неизвестный email, даёт одинаковые 401 code/message; ответ не подтверждает существование пользователя. Структурно некорректный JSON/отсутствующие обязательные поля → 400. Ограничение попыток → 429 с Retry-After по N04, недоступное обязательное хранилище → 503 по R05.

Access подписанный JWT сроком ровно 15 минут. Refresh — криптографически случайный непрозрачный токен, не менее 32 случайных bytes, в БД только его digest. Новая login-сессия имеет абсолютный срок не более 30 дней. Ответы с токенами не кэшируются и не попадают в логи. Отличие длительности ответов неизвестного email не объявляется устранённым без измерения; планируется одинаковый путь проверки hash с dummy hash.

### F03 — Обновление сессии

Валидный неистёкший и неотозванный refresh одноразово и атомарно заменяется новой парой. Старый refresh после успеха → 401; при двух одновременных попытках только одна успешна. Invalid/expired/revoked/used refresh возвращают одинаковые 401 без раскрытия причины.

Ротация сохраняет абсолютный конец 30-дневной login-сессии, не прибавляет новые 30 дней к каждой попытке. Новый refresh не живёт дольше сессии. Access TTL остаётся ≤15 минут; рядом с окончанием сессии refresh уже может истечь раньше access — это допустимо, access всё равно имеет предел N03. Replay старого refresh сам по себе не отзывает новую пару — family-reuse revocation не включено скрытым требованием. Замена token-records транзакционна.

### F04 — Выход

Выход отзывает refresh указанной текущей сессии; другие login-сессии не затрагиваются. Доказательство владения сессией — предъявление её refresh; точное требование Bearer для операции будет зафиксировано на этапе 2 так, чтобы истёкший access не мешал отзыву refresh. Повтор logout безопасен, одинаковый успешный ответ для уже отозванного/неизвестного корректно оформленного токена, без сообщения о наличии сессии.

После выхода refresh этой сессии не работает. Уже выданный JWT автоматически не исчезает и может действовать до expiry ≤15 минут. Немедленный отзыв access не обещается исходным F04 и в этот baseline не добавлен.

### F05 — Восстановление пароля

Запрос forgot для синтаксически валидного известного/неизвестного email возвращает одинаковые 202/body. Для известного email создаётся одноразовый token со сроком 15 минут и ссылкой доставки через IEmailSender. Исходный token не хранится в открытом виде, не возвращается HTTP-клиенту forgot и не логируется. Новый запрос инвалидирует предыдущие неиспользованные reset tokens пользователя — предлагаемое уточнение.

В Development/test sender удерживает письмо в памяти с ограниченным временем жизни для локальной проверки через тестовую зависимость; публичный endpoint для чтения чужих писем не создаётся. В production понадобится реальный sender, его работа сейчас не проверяется.

При reset валидируются новый пароль и token. В одной транзакции: меняется hash, token помечается использованным, отзываются **все** refresh пользователя. Повторный/invalid/expired reset → единая 400; при точном now==expiry token уже недействителен. Две конкурентные попытки не могут обе сменить пароль. После reset старый пароль не подходит. Выданные ранее JWT остаются максимум до expiry по той же политике, что F04. Структурно неверный forgot/reset → validation 400; DB failure → 503, без ложного успеха.

### F06 — Создание подписки

Только аутентифицированный пользователь создаёт собственную подписку: Name, Amount, Currency, BillingPeriod, Category, StartDate, NextPaymentDate. Валидация — раздел 3; `NextPaymentDate ≥ StartDate`. Начальная next date может быть в прошлом, чтобы внести уже действующую подписку. Отсутствующий/некорректный параметр → 400 и никаких строк.

При создании Status=Active, Archived=false. Сохраняется original billing day и original billing month из NextPaymentDate, а также сама точка отсчёта расписания. Для monthly month не влияет на шаг, для yearly нужен для восстановления 29 Feb. Периодичность начинается с NextPaymentDate, а не с повторной генерации от StartDate.

### F07 — Получение подписок

List выдаёт только текущего владельца. По умолчанию Archived=false. Есть фильтры status и category; отдельное явное включение archived должно быть описано на этапе API. Сортировка — NextPaymentDate asc, затем Id asc; пагинация — раздел 3. Прочтение своей подписки по ID возвращает её, в том числе archived с явным признаком. Чужая/несуществующая → 404 без различий, invalid ID syntax → 400. Никакой UserId из query/body не позволяет расширить область данных.

### F08 — Изменение подписки

Владелец может менять Name, Amount, Currency, BillingPeriod, Category и будущую NextPaymentDate у неархивной Active/Paused подписки. Новая дата, если передана, строго позже UTC today и не раньше StartDate. Для изменения BillingPeriod одновременно указывается новая NextPaymentDate. Изменение других полей не вынуждает переписать старую next date, даже если она уже прошла.

Явная новая next date задаёт новый anchor day/month; изменение суммы/названия/валюты/категории anchor не меняет. Original billing day не переписывается при clamp короткого месяца. StartDate и владелец после создания не меняются в учебном API.

Cancelled/archived расписание неизменно; попытка обновления → 409, чужой ID →404, невалидные значения →400. В платежах уже сохранены исторические поля и snapshot-категория/название: обновление подписки не переписывает их и не меняет прошлые расходы. Запись факта оплаты сама не передвигает NextPaymentDate.

### F09 — Статусы подписки

| Текущее состояние | Команда | Результат |
|---|---|---|
| Active | pause | Paused |
| Paused | resume | Active |
| Active / Paused | cancel | Cancelled |
| Paused | pause | Paused, безопасный повтор |
| Active | resume | Active, безопасный повтор |
| Cancelled | cancel | Cancelled, безопасный повтор |
| Cancelled | pause / resume | 409, Cancelled терминальный |
| Любой Archived | pause / resume / cancel | 409, архив не меняет расписание |

Чужая/отсутствующая подписка →404. Resume не переносит anchor и не восстанавливает пропущенные факты. Paused/Cancelled не участвуют в прогнозе. Эти правила — предложенное разрешение исходной неопределённости, не ранее существовавший контракт.

### F10 — Архивация

Удаление — только Archived=true, без физического удаления подписки или её платежей/audit. Владелец может архивировать Active/Paused/Cancelled; повтор archive безопасен и успешен. Status сохраняется отдельно от flag. Архив скрыт из обычного list и forecast, detail владельцу и history остаются доступны. Удаления архива/разархивации в объём не добавляем.

Успешные неаннулированные факты архивной подписки участвуют в расходах. Регистрация пропущенного ручного исторического факта для своей archived/cancelled подписки разрешена по F11; это не возобновление списаний. Изменение расписания архива запрещено по F08/F09.

### F11 — Регистрация факта платежа

Только для собственной существующей подписки, включая paused/cancelled/archived. Обязательны positive Amount в пределах раздела 3, Currency точно равная **текущей** валюте подписки на момент регистрации, Date≤UTC today и Status successful/failed. Вводимый факт хранит свою amount/currency/date/status, UserId/SubscriptionId, CreatedAt/UpdatedAt, IsVoided=false, снимок category/name на момент внесения факта. Дата внесённого факта может быть исторической; исторический currency-конвертер/версионированный каталог категорий не добавляются.

Idempotency-Key обязателен: 1–128 видимых ASCII, без пробелов, учитывается точно и регистрозависимо. Scope — пользователь + операция create-payment + key; SubscriptionId входит в идентичность payload, поэтому тот же ключ на другой подписке — 409. JSON order/пробелы и 1.0/1.00 не делают payload разным; сравниваются типизированные значения даты/суммы/валюты/status и SubscriptionId, неизвестные поля тела — validation 400. Actor/серверные timestamp не входят в payload comparison.

- Новый ключ + валидные данные — ровно один payment, idempotency record с неизменным первым успешным HTTP-ответом, create audit; единая транзакция R04.
- Тот же ключ + те же значения — первоначальный status/body/resource ID без второй записи и второго аудита, даже если payment позднее изменили/аннулировали или подписку переименовали/архивировали/сменили валюту. Ownership по-прежнему обязателен. Replay проверяется по сохранённому original payload, а не по текущему состоянию подписки.
- Тот же ключ + другой payload —409, без изменений. Два конкурентных одинаковых запроса не создают два платежа; конфликт unique разрешается как replay/conflict, не 500.
- Другой ключ — новая операция. Без явного TTL ключи живут весь срок сохранности учебной БД. Ошибки валидации/отказ транзакции не резервируют успешный результат; при неясном результате commit нужен повтор с тем же ключом.

Без Bearer →401, чужая/несуществующая subscription →404, входные ошибки/валюта →400. «Неуспешный платёж» — пользовательский сохранённый факт со Status=failed, а не ошибка HTTP записи.

### F12 — История платежей

Только собственные платежи; фильтры SubscriptionId, Status и диапазон Date. Две переданные границы включены, from≤to; при одной границе применяется односторонний фильтр; при отсутствии обеих доступна вся история с пагинацией. Максимум 366 дней относится к аналитике N07, не вводится молча в history.

Порядок Date desc, затем Id asc; page/pageSize по разделу 3. Все payment statuses и voided по умолчанию видимы с явными полями. Archived подписки не исключают их историю. Чужой/несуществующий SubscriptionId-фильтр →404, malformed/invalid filters →400. Query UserId не поддерживается. Пустой список/страница — успешный пустой результат, не 404.

### F13 — Исправление и аннулирование

Владелец исправляет Amount, Date и Status у неаннулированного платежа; сумма и дата соответствуют разделу 3. Currency, SubscriptionId, UserId и снимки category/name неизменны. Поэтому старый RUB payment можно корректировать после изменения валюты подписки на USD: currency самого факта остаётся RUB, сверка с новой валютой подписки при correction не производится.

Void ставит IsVoided=true, не удаляет строку. Повторный void успешен и не создаёт фиктивное повторное изменение/audit. Возврат voided в активный и correction voided →409; чужой/неизвестный payment →404; invalid input→400. История архива не блокирует исправление факта.

Каждое реальное изменение создаёт append-only audit с actor ID, действием, UTC time, previous-values и new-values. У create previous=null; у correction/void previous — точное предыдущее состояние, а не значения из запроса. Изменение записи и audit в одной транзакции. Чтение history должно давать доступ владельцу к истории изменений; точный формат/точка доступа определяются на этапе 2. Доступ другого пользователя к audit →404.

### F14 — Расходы

Для явно переданных календарных from и to, `[from,to]` включительно, длина `to−from+1≤366 дней`, from≤to. Пропуск обязательной границы, невалидная дата или превышение →400. Учитываются только собственные Status=successful, IsVoided=false платежи с Date в диапазоне. Archived/cancelled/paused состояние подписки не исключает уже состоявшийся расход.

Результат содержит totals by currency и breakdown by calendar month (YYYY-MM), category snapshot и SubscriptionId. Каждая breakdown-группа имеет отдельную валюту; группировка по подписке не сливает старую RUB и новую USD. Ключ разбивки по подписке — SubscriptionId+Currency; в этой разбивке достаточно ID без спорного единственного названия, если snapshots различаются. Сохранённое название остаётся в истории фактов и не меняет ключ группировки.

При отсутствии данных totals содержит RUB=0/USD=0/EUR=0; breakdown arrays пустые. Для непустой выборки totals тоже содержит все три валюты с нулями для отсутствующих. Месяцы без расходов не создаются автоматически. Используются точные decimal суммы, конвертации и единого межвалютного total нет.

### F15 — Прогноз

Read-only прогноз текущего владельца на `[UTC today, UTC today+30 дней)`, то есть ровно 30 календарных дат с включением сегодняшней. Учитываются только Active && !Archived subscriptions. Выход: каждая дата/SubscriptionId/название/amount/currency и totals RUB/USD/EUR отдельно, с 0 при отсутствии событий. Порядок date asc, затем SubscriptionId asc.

Расписание вычисляется от сохранённого NextPaymentDate/anchor:

- monthly: месяц очередного события + original billing day; если дня нет, последний день месяца;
- yearly: год очередного события + original billing month/day; 29 Feb в обычном году →28 Feb, в следующем високосном снова29 Feb;
- каждый шаг вычисляется от **исходного** anchor, а не от результата clamp предыдущего события; day=31 после февраля снова31 в марте;
- кандидаты раньше NextPaymentDate или StartDate не создаются; просроченное расписание продвигается расчётом до первого кандидата в окне, старые даты не выдаются и в БД ничего не переписывается;
- amount/currency берутся из текущей подписки, будущие факты оплаты не создаются; зарегистрированный вручную платёж не сдвигает и не подавляет событие расписания.

30-дневное окно иногда может содержать два monthly события, например 31 Jan и 28 Feb — нужно вернуть оба, а не «одну сумму на подписку». Пустая выборка успешна. Без авторизации →401. Параметры произвольного forecast window не добавляются: часы подменяются только в тестах, не публичным UserId/asOf для обхода ограничений.

## 5. Нефункциональные требования

### N01 — Транспорт

Сохранено HTTPS TLS1.2+ для внешнего API. Учебный запуск допускает HTTP на localhost/loopback только Development с явным описанием. Запуск на 0.0.0.0 с HTTP не объявляется внешним защищённым сервисом. Подтверждение TLS при внешнем развёртывании — отдельный будущий тест; localhost smoke его не заменяет.

### N02 — Пароли

Основной вариант Argon2id, уникальная криптографически случайная соль ≥16 bytes, versioned hash format с параметрами. Библиотека и конкретные memory/time/parallelism параметры должны быть проверены перед Auth на .NET10/macOS; benchmark и адаптация мощности не выполнены сейчас. Самописный KDF не допускается.

ASP.NET Core PasswordHasher может быть предложен только отдельным явно объяснённым отклонением с алгоритмом/параметрами и тестами. В этой редакции такое отклонение **не принято и не утверждается**, Argon2id не удалён. Пароли, hash и соль не возвращаются в DTO/логах.

### N03 — Токены

Access ≤15 минут, refresh ≤30 дней и абсолютный срок сессии по F02/F03. Валидация JWT: signature, допустимый алгоритм, issuer, audience, expiration; ClockSkew=0. Expiry boundary: now≥expiresAt означает invalid. Часы UTC. Refresh/reset secrets генерируются криптографически, хранятся digest; JWT signing secret не в репозитории/отчёте/реальных логах. Для будущего запуска используется внешняя конфигурация/временный секрет, не сдаваемый действующий ключ.

### N04 — Лимиты входа (явное учебное упрощение)

Rolling 15 минут: максимум 5 неудачных credential checks на нормализованный email и 30 login attempts на IP. Первые 5 неверных —401, при наличии 5 неудач следующий login email —429, правильный пароль не обходит lockout. Первые 30 запросов IP допускаются к дальнейшим проверкам, 31-й —429. Неизвестный нормализуемый email учитывается так же. Невалидный body может дать400, но занимает IP attempt; IP admission до разбора credentials, а общий body limit N07 ещё действует.

Считаются только реально разрешённые IP admission; запросы, заблокированные IP, не продлевают его окно. Account-blocked запросы занимают IP attempt, но не создают новый credential failure. Успех не стирает неудачи. На каждой границе окна старая попытка с age≥15 минут удаляется. При запрете Retry-After — ceil оставшихся секунд (≥1), для одновременного запрета обоими лимитами — max. Ответ ошибки Q04 без информации о существовании email.

План: exact rolling timestamp state и атомарные проверки; IP — in-memory middleware одного экземпляра, очистка неактивных IP; account — абстракция и персистентные timestamps в SQLite. Произвольный Forwarded-For не принимается, RemoteIpAddress/настроенный trusted proxy. In-memory IP-state теряется при рестарте, распределённый IP-limit не гарантируется: **это предлагаемое учебное упрощение**, не полное production N04. Оно не исключает ни один из двух лимитов из будущих локальных тестов.

### N05 — Производительность: отдельные испытания

Сохранить: p95 CRUD≤300 ms, аналитика≤1 s, 5xx<1%, 100 req/s, 100 параллельных клиентов, 1 млн платежей. Уточняем аналитический предел как p95≤1 s; в нагрузочном плане отдельно указать, что исходная формулировка не задавала percentile аналитики. Требуются профиль операций, dataset/distribution, warm-up, duration, hardware, ресурсы SQLite и способ учёта ошибок. Текущий статус requires performance testing. Ни время единичного curl, ни unit tests не подтверждают N05.

### N06 — Форматы (без изменения исходного требования)

JSON UTF-8; префикс `/api/v1`; DateTime ISO8601 UTC; календарные даты YYYY-MM-DD; деньги decimal, не double; без автоматической конвертации валют. Дополнительные диапазоны данных определены в F06/F11 и разделе 3, а не приписываются исходному N06.

### N07 — Ограничения API

Тело ≤1 MiB=1048576 bytes фактически прочитанных данных, включая запрос без Content-Length; превышение →413. Размер страницы ≤100, недопустимые page values →400. Аналитический диапазон включительно ≤366 дней, invalid→400. Общая ошибка Q04 действует на 413, если запрос дошёл до HTTP application pipeline; transport-level malformed HTTP/TLS не выдаются за обработанный middleware запрос.

### N08 — Correlation и журналирование

Каждый app-generated HTTP response, включая 400/401/404/409/413/429/503, содержит X-Correlation-ID. В error JSON тот же correlationId. Валидный внешний ID можно принять только после проверки длины/символов (предлагается 1–64, ASCII буквы/цифры/дефис/подчёркивание); иначе генерировать новый. Лог: route template, status, duration ms, correlation ID. Не логировать query string с reset token, body, password, Authorization, refresh/reset/signing secrets или полное письмо восстановления. Не возвращать stacktrace/внутренний путь БД.

### N09 — Контейнеризация

Добавить Dockerfile с внешней конфигурацией и отдельным путём/volume для SQLite, если это не блокирует основной объём; факт отсутствия Dockerfile должен быть отражён как partial. Linux x64/arm64 runtime и сборка контейнера проверяются только реальным запуском; macOS arm64 не доказывает их. Наличие Dockerfile само по себе не означает Docker tested.

### N10 — OpenAPI

Документ содержит все реализованные endpoints, path/query/body, request/response schemas, статус-коды успеха и ошибок, Bearer security и какие операции публичны. Swagger UI локально в Development. Должны быть реально проверены доступность OpenAPI JSON и UI; ожидаемый вид документа не выдаётся за полученный. Точный API-контракт создаётся только на этапе 2.

## 6. Требования качества

### Q01 — Проверки требований (без изменения)

Для каждого F01–F15 запланированы позитивные и негативные проверки. Различать unit (без HTTP/реальной БД), API/integration (реальный pipeline и изолированная SQLite), smoke (реальный процесс и curl). План ниже не означает, что тесты написаны или прошли.

### Q02 — Coverage

Analytics и Forecast **каждый отдельно** ≥90% branch coverage; включить реализующие алгоритмы бизнес-классы, не прятать их ветви exclude-атрибутами. Обязательны leap year, end-of-month, empty period, разные валюты и voided payment. Общий бизнес-охват из PDF и запроса: >80% branch и >90% statement, если statement метрика действительно доступна.

Измеряется Application/Services и Domain business logic, с обоснованным исключением Program/generated/migrations/DTO без логики/infrastructure boilerplate. Все реальные бизнес-ветви остаются в знаменателе. Если инструмент выдаёт только line/branch, line не называется statement. Проверить возможность точной statement/instruction метрики другим инструментом/форматом; при отсутствии честно оставить statement unverified и отдельно представить line/branch. Analytics/Forecast нельзя замаскировать общим процентом других сервисов. Никаких чисел coverage на этапе 1 нет.

### Q03 — Изоляция бизнес-логики (без изменения)

Бизнес-логика зависит от абстракций. Unit tests не требуют сети, реальной внешней БД, отправки email. Реальный SUT, Moq только для repositories/clock/token generator/email/инфраструктуры. Проверки настоящей SQLite transaction относятся к integration, не называются unit. Business services не зависят от HTTP/EF напрямую; controllers только адаптируют запрос/ответ.

### Q04 — Единый формат ошибки (без изменения)

JSON содержит code, message, correlationId; fields обязательно для validation и не обязательно для остальных ошибок. Возврат 401 сохраняет соответствующие auth headers, 429 — Retry-After. В схемах OpenAPI эти ошибки документируются. Наличие формата не означает, что нужно скрыть внутренний дефект как успешный ответ.

### Q05 — Финальная проверка и ownership (без изменения)

Build без ошибок, желательно без warnings; тесты без failed; нет доступа к чужим ресурсам. Все resource-ID операции, включая filtered history, correction, void, transitions, archive, audit, проверяют owner. UserId из запроса не используется для выдачи чужих данных. Финальное требование относится к будущей реализации, не текущему этапу документов.

## 7. Надёжность

### R01 — Availability, documented only

Сохранено availability≥99.5%. Предлагаемый период оценки — календарный месяц, среда и исключения должны быть согласованы в эксплуатационном SLO. Длительный мониторинг/внешние probes ещё не проводились. Unit/API/smoke лабораторной не подтверждают R01.

### R02 — Backup, production requirement и учебная альтернатива

Сохранить исходное ежедневное резервирование БД и интервал transaction-log backup≤15 минут для production. Для SQLite WAL нельзя объявлять архивом PITR. Предлагаемая учебная интерпретация — согласованный snapshot через SQLite Online Backup API или эквивалент, не реже15 минут плюс сохраняемый daily backup; расписание/хранилище/retention надо документировать отдельно. Это замена механизма для учебной SQLite, не доказательство оригинального transaction-log требования.

На текущем этапе ни scheduler, ни backups, ни recovery не реализованы. Не заявлять R02 выполненным по наличию SQL/seed/Dockerfile. Production PITR остаётся documented only; если учебный backup будет реализован, его фактический статус и ограничения отражаются отдельно.

### R03 — RPO/RTO, requires operational testing

Сохранить RPO≤15 минут, RTO≤60 минут. Для подтверждения нужны реальный backup, контроль его возраста, потеря/недоступность основной БД, восстановление в новое хранилище, integrity check и повторный запуск/проверка данных API с замером времени. Пока требования не проверены; обещание RPO из одной частоты cron недопустимо.

### R04 — Транзакционность

Создание payment+idempotency record+create audit атомарно в одной SQLite transaction. При rollback нет ни одной из трёх частичных записей, initial response записывается согласованно с payment. Unique key защищает scope F11. Unit проверяет обращение к transactional abstraction; integration fault injection после промежуточных writes доказывает отсутствие частичного состояния. Correction/void также атомарны с собственным audit по F13. Успешный HTTP-ответ только после подтверждённого commit.

### R05 — Недоступная БД

При unavailable/busy/IO failure обязательной БД вернуть generic503 без ложного сообщения о записи; процесс остаётся работоспособен для последующих запросов после восстановления. Конкретные распознаваемые SQLite errors/таймауты и статус health endpoint будут определены при API/инфраструктуре. Unique email/идемпотентность —409/повтор, не «недоступность»; bugs —500 единым форматом, не скрытые503.

Если commit мог состояться, но подтверждение потеряно, не обещать отсутствие записи: результат неопределён, клиент повторяет тот же Idempotency-Key для разрешения. Integration проверяет реальную неудачную транзакцию/отсутствие2xx и recovery; это не подменяется одним mock throwing exception.
